# خطة أتمتة اختبارات Flutter عبر GitHub Actions

## الهدف

تهدف هذه الخطة إلى جعل كل تغيير في مشروع `smart-accountant` قابلًا للتحقق تلقائيًا قبل دمجه في `main`. ستشغّل GitHub Actions التحليل الساكن، اختبارات الوحدة والودجت، اختبارات التكامل، تقرير التغطية، وفحوصات الأمان، ثم تمنع الدمج أو بناء APK إذا فشلت أي بوابة جودة إلزامية.

## الوضع الحالي

يحتوي المشروع بالفعل على سير عمل في `.github/workflows/build.yml` بثلاثة مسارات جودة رئيسية: `fast` للتحليل والتنسيق والاختبارات، و`full` للاختبارات والتغطية والتكامل، و`security` لفحص الأسرار والاعتماديات. كما يحتوي `tooling/ci_local.sh` على أوضاع `fast` و`full` و`security`، ويستخدم Flutter `3.27.1`.

يوجد حاليًا مساران لاختبارات التكامل:

| الملف | نطاق الاختبار |
|---|---|
| `test/integration_workflow_test.dart` | تدفق صوتي غير متصل إلى SQLite وتصدير Excel وحالات البيع والأمر غير المكتمل |
| `test/integration_full_workflow_test.dart` | التقاط Vosk محاكى، معالجة الأمر، التخزين، التقارير اليومية، تصدير PDF وExcel، وعدم حفظ الأمر غير المكتمل |

تبلغ التغطية الحالية **86.81% — 1093/1259** وفق آخر تقرير LCOV، وهي أعلى من بوابة الجودة الحالية البالغة 70%.

## التصميم المقترح لسير العمل

### 1. تشغيل سريع لكل Pull Request وPush إلى `main`

يُنفذ هذا المسار في أقل وقت ممكن، ويشمل `flutter pub get`، التحقق من التنسيق عبر `dart format --set-exit-if-changed`، ثم `flutter analyze`. بعد ذلك يشغّل اختبارات الوحدة والودجت فقط، مع استبعاد الاختبارات الموسومة أو المصنفة كتكاملية إن تم اعتماد tags لها.

الأمر المقترح هو:

```bash
./tooling/ci_local.sh fast
```

يجب أن تكون نتيجة هذا المسار شرطًا إلزاميًا للدمج، لأنه يعطي تغذية راجعة سريعة على أخطاء Dart والتحليل والاختبارات الأساسية.

### 2. تشغيل اختبارات التكامل لكل Pull Request

يُشغّل هذا المسار بعد المسار السريع أو بالتوازي معه، ويستخدم بيئة Linux ثابتة مع SQLite FFI وFlutter نفسه. ينفذ الاختبارين الحاليين صراحةً بدل الاعتماد على اكتشاف الملفات:

```bash
flutter test test/integration_workflow_test.dart --concurrency=1
flutter test test/integration_full_workflow_test.dart --concurrency=1
```

يفضل تشغيل الاختبارات بالتسلسل باستخدام `--concurrency=1` لأن قاعدة SQLite المحلية وموارد الاختبارات قد تتشارك الحالة. يجب ضبط `SharedPreferences` وتنظيف جدول `transactions` في `setUp` وإغلاق قاعدة البيانات في `tearDown` كما هو مطبق حاليًا.

### 3. تقرير التغطية وبوابة الحد الأدنى

بعد نجاح اختبارات الوحدة والودجت والتكامل، يُشغّل الاختبار الكامل مع التغطية:

```bash
flutter test --coverage --concurrency=1
```

ثم يُتحقق من وجود `coverage/lcov.info`، ويُحسب الإجمالي من حقلي `LF` و`LH`. يجب إبقاء الحد الحالي عند 70% في المرحلة الأولى، ثم رفعه تدريجيًا إلى 75% وبعدها 80% بعد استقرار الاختبارات. يمكن استخدام سكربت التحليل الموجود في `tooling/report_coverage.py` لإنتاج ترتيب التغطية حسب الملف، مع رفع `coverage/lcov.info` و`coverage/html/` كـ artifacts.

البوابة المقترحة:

| الشرط | السلوك عند الفشل |
|---|---|
| ملف LCOV غير موجود أو فارغ | فشل الوظيفة |
| التغطية أقل من 70% | فشل الوظيفة ومنع الدمج |
| انخفاض التغطية عن خط أساس Pull Request | تحذير في المرحلة الأولى، ثم شرط إلزامي بعد تثبيت الأداة |
| فشل اختبار واحد | فشل الوظيفة |

### 4. فحص الأمان

يستمر مسار `security` الحالي لفحص الأسرار عبر Gitleaks، وفحص اعتماديات Dart عبر OSV Scanner، ومراجعة الاعتماديات في Pull Requests. يجب الاحتفاظ برفع SARIF إلى GitHub Code Scanning، مع جعل الثغرات عالية الخطورة حاجزًا يمنع الدمج.

### 5. بوابة موحدة للدمج والبناء

تستمر وظيفة `quality` في انتظار `fast` و`full` و`security`. لا يُسمح ببناء APK أو نشر إصدار إلا إذا كانت وظيفة `quality` ناجحة. يبقى بناء APK مقتصرًا على tags من نمط `v*`، مع استخدام Java 21 وFlutter 3.27.1 كما في الإعداد الحالي.

## تحسين مقترح لملف CI المحلي

يُستحسن إضافة وضع صريح باسم `integration` إلى `tooling/ci_local.sh` بدل تكرار الأوامر في YAML:

```bash
run_integration() {
  step "Integration tests"
  flutter test test/integration_workflow_test.dart --concurrency=1
  flutter test test/integration_full_workflow_test.dart --concurrency=1
}
```

ثم يصبح الاستخدام:

```bash
./tooling/ci_local.sh integration
```

ويُستحسن تعديل وضع `full` ليشغّل `run_fast` ثم `run_integration` ثم `run_coverage`، مع إبقاء التقرير والتغطية artifacts حتى عند فشل الاختبارات باستخدام `if: always()` في GitHub Actions.

## استراتيجية المحفزات

| المحفز | الوظائف المطلوبة |
|---|---|
| Pull Request إلى `main` | `fast`، اختبارات التكامل، التغطية، الأمان، بوابة الجودة |
| Push إلى `main` | الوظائف نفسها للتأكد من حالة الفرع بعد الدمج |
| Tag من نمط `v*` | بوابة الجودة ثم بناء APK وإنشاء Release |
| تشغيل يدوي | جميع الوظائف مع إمكانية تشخيص فشل بيئي أو إعادة إصدار تقرير |
| تشغيل أسبوعي اختياري | جميع الاختبارات لاكتشاف انكسار الاعتماديات أو تغير البيئة حتى دون تغييرات جديدة |

## تحسينات الاعتمادية والأداء

يجب استخدام caching في `subosito/flutter-action` وGradle كما هو موجود، مع تثبيت نسخة Flutter صريحة وعدم استخدام `channel` وحده. ينبغي تحديد `timeout-minutes` لكل وظيفة، واستخدام `concurrency` على مستوى workflow لإلغاء التشغيل الأقدم لنفس Pull Request عند وصول commit جديد. كما يجب حفظ سجلات الاختبارات والتغطية عند الفشل، وليس فقط عند النجاح.

يمكن تشغيل `fast` و`security` بالتوازي، وتشغيل التكامل والتغطية بالتوازي مع `fast` إذا لم تكن هناك حاجة إلى نتائج `fast` مسبقًا. أما `quality` فينتظر جميعها. هذا يقلل زمن التغذية الراجعة مع الحفاظ على بوابة موحدة.

## التقارير المطلوبة في كل تشغيل

ينبغي أن ينتج التشغيل الملفات التالية كـ artifacts:

| artifact | المحتوى | مدة الاحتفاظ المقترحة |
|---|---|---:|
| `coverage-${{ github.sha }}` | `coverage/lcov.info` و`coverage/html/` | 14 يومًا |
| `integration-logs-${{ github.sha }}` | سجلات اختبارات التكامل عند الفشل | 14 يومًا |
| `security-${{ github.sha }}` | SARIF الخاص بـ OSV ونتائج الفحص | 30 يومًا |
| `performance-${{ github.sha }}` | نتائج الأداء عند إضافة مجلد الأداء | 14 يومًا |

يفضل إضافة ملخص إلى `GITHUB_STEP_SUMMARY` يذكر عدد الاختبارات، نسبة التغطية، الحد الأدنى، ونتيجة كل بوابة. بذلك يستطيع المراجع رؤية النتيجة دون تنزيل الملفات.

## خطة التنفيذ المرحلية

### المرحلة الأولى: تثبيت الوضع الحالي

تأكيد أن `fast` و`full` و`security` تعمل محليًا وداخل GitHub Actions، وإضافة `test/integration_full_workflow_test.dart` إلى المسار الكامل. توثيق حد التغطية الحالي البالغ 70%.

### المرحلة الثانية: فصل التكامل عن الاختبارات السريعة

إضافة وضع `integration` إلى `tooling/ci_local.sh`، وتشغيل اختبارات الوحدة والودجت في `fast`، واختبارات التكامل في وظيفة مستقلة. يجب أن تبقى جميع الوظائف تحت `quality`.

### المرحلة الثالثة: تحسين التقارير

إضافة ملخص GitHub للنتائج ورفع artifacts عند النجاح والفشل. تضمين تقرير الملفات الناتج عن `tooling/report_coverage.py` أو دمجه في ملخص التشغيل.

### المرحلة الرابعة: بوابة الانحدار

بعد تثبيت التغطية، حفظ baseline للفرع `main`، ثم جعل Pull Request يفشل إذا انخفضت التغطية الإجمالية أو تغطية الملفات الحرجة، مثل `ai_agent_service.dart` و`audio_ports.dart`، دون الحاجة إلى رفع الحد العام فجأة.

### المرحلة الخامسة: التوسع المستقبلي

عند إضافة اختبارات أداء داخل `test/performance/`، يُفصل تشغيلها في وظيفة اختيارية أو أسبوعية حتى لا تطيل كل Pull Request. ويمكن إضافة مصفوفة اختبار لأنظمة أو إصدارات Flutter عند الحاجة، لكن يفضل البدء ببيئة Linux واحدة ثابتة لتقليل زمن التشغيل والتذبذب.

## معايير القبول

تعد الخطة منفذة بنجاح عندما يحقق المشروع الشروط التالية:

1. يفشل Pull Request تلقائيًا عند فشل `flutter analyze` أو أي اختبار وحدة أو تكامل.
2. يظهر تقرير LCOV كـ artifact في التشغيل الناجح والفاشل.
3. تمنع بوابة التغطية الدمج إذا انخفضت النسبة عن الحد المحدد.
4. تمنع وظيفة `quality` بناء APK عند فشل أي من `fast` أو `integration/full` أو `security`.
5. تظهر نتيجة مختصرة في GitHub Actions Summary دون الحاجة إلى قراءة السجل الكامل.
6. يبقى التشغيل قابلاً لإعادة التنفيذ يدويًا، مع مهلة وفشل واضحين عند مشاكل البيئة.
7. لا تستخدم الاختبارات التكاملية خدمات خارجية أو أسرارًا حقيقية؛ تعتمد على fakes وSQLite FFI كما في الاختبارات الحالية.

## التوصية التنفيذية

البنية الحالية قريبة من المطلوب، لذلك لا يلزم إنشاء Workflow جديد بالكامل. التغيير الأقل مخاطرة هو إضافة وضع `integration` إلى `tooling/ci_local.sh`، فصل وظيفة التكامل عن `full` في `build.yml`، إضافة artifacts وملخص التغطية، ثم إبقاء `quality` كبوابة وحيدة قبل الدمج أو بناء APK. هذا يحافظ على التصميم الموجود ويجعل فشل اختبارات الوحدة والتكامل ظاهرًا ومحددًا وقابلًا لإعادة التشغيل.
