# HMAC and replay hardening

## إدارة المفتاح

ضع مفاتيح HMAC في Secret Manager أو خدمة مفاتيح سحابية، ولا تضعها في Git أو Docker image أو سجلات CI. حمّل المفتاح عند بدء الخدمة أو عبر آلية تدوير آمنة، واسمح بوجود مفتاح `current` ومفتاح `previous` لفترة انتقالية قصيرة. استخدم `X-Webhook-Key-Id` لاختيار المفتاح، لكن لا تعتبر المعرّف سراً ولا تقبل إلا قائمة مفاتيح معروفة.

قيّد صلاحية قراءة المفتاح إلى حساب الخدمة، وفعّل Redis TLS وACL، وامنع الوصول العام إلى Redis. دوّر المفتاح دورياً، وأبطل المفتاح القديم بعد انتهاء نافذة التوافق. لا تسجل قيمة المفتاح أو التوقيع الكامل أو body الخام.

## توقيع الطلب

وقّع البايتات الخام قبل أي parsing بالصيغة `HMAC-SHA256(key, timestamp + "." + raw_body)`. استخدم مقارنة ثابتة الزمن، وارفض الطلب إذا كان timestamp غير رقمي أو خارج نافذة قصيرة مثل 5 دقائق. اربط التوقيع بالطريق والمحتوى ونوع الحدث، وطبّق حد حجم و`Content-Type: application/json` وschema validation.

## منع Replay

استخدم `X-Webhook-Id` مستقراً من المصدر، أو hash للbody عند غيابه، مع `SET key hash NX EX ttl` أو Lua script ذري في Redis. إذا كان المفتاح موجوداً بنفس hash فهذه إعادة إرسال مطابقة آمنة؛ وإذا اختلف hash فأعد `409` وسجّل conflict منقحاً. اجعل TTL أكبر قليلاً من نافذة retries، واربط namespace بالبيئة والمصدر، ولا تستخدم `KEYS` أو `MONITOR` في الإنتاج.

أضف rate limiting، TLS، allowlist للشبكات أو mTLS عند الإمكان، timeouts، وقيوداً على عدد العمال. لا تعتبر HMAC بديلاً عن المصادقة على هوية المستهلك؛ يجب أن يكون لكل مصدر key مستقل مع صلاحيات وقناة منفصلة.

## التحقق والاختبار

اختبر توقيعاً صحيحاً، body معدلاً، timestamp قديماً أو مستقبلياً، key-id غير معروف، replay بنفس body، replay مع body مختلف، Redis unavailable، وkey rotation. يجب ألا ينتج replay أثراً ثانياً، ويجب ألا تكشف الاستجابات أو السجلات أسراراً.
