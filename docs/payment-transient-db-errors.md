# التعامل الآمن مع أخطاء قاعدة البيانات المؤقتة أثناء ضغط الدفع

## المبدأ الأساسي

اعتبر `deadlock` و`serialization failure` و`lock timeout` أخطاء قابلة لإعادة المحاولة فقط عندما تكون المعاملة قابلة للإعادة بأمان، ومفتاح `Idempotency-Key` محفوظاً ومفروضاً بصفة UNIQUE. يجب ألا تعني إعادة المحاولة إنشاء دفعة جديدة؛ بل إعادة تنفيذ نفس العملية المنطقية داخل معاملة جديدة.

## الأخطاء القابلة لإعادة المحاولة

صنّف أخطاء محرك قاعدة البيانات عبر أكوادها الرسمية، لا عبر مطابقة نص الرسالة فقط. أمثلة شائعة: PostgreSQL `40P01` للـdeadlock و`40001` لفشل serialization، وMySQL `1213` للـdeadlock و`1205` لـlock wait timeout. راجع driver المستخدم قبل اعتماد القائمة، لأن الأكواد تختلف بين المحركات.

لا تعِد المحاولة مع أخطاء التحقق، الصلاحيات، البيانات غير الصالحة، قيد uniqueness غير المتوقع، أو فشل schema. هذه أخطاء نهائية تحتاج إصلاح الطلب أو النظام.

## نمط المعاملة

1. ابدأ معاملة قصيرة.
2. أنشئ أو تحقّق من سجل idempotency بمفتاح فريد قبل إنشاء الأثر المالي.
3. اقفل الصفوف بترتيب ثابت، وحدث ledger والدفعة ضمن نفس المعاملة.
4. نفذ commit.
5. بعد commit فقط أرسل event أو webhook.
6. عند deadlock، نفذ rollback كاملاً ثم انتظر backoff مع jitter وابدأ معاملة جديدة بنفس المفتاح.

استخدم `SELECT ... FOR UPDATE` بحذر، وقلل نطاق الأقفال ومدة المعاملة. لا تحتفظ باتصال أو transaction أثناء استدعاء شبكة أو مزود دفع خارجي.

## سياسة retry

استخدم حداً أقصى منخفضاً مثل 2 أو 3 محاولات، وexponential backoff مع jitter، مع احترام `Retry-After` عند الحاجة. لا تستخدم retry متزامناً لكل الطلبات؛ أضف random jitter وbulkhead وحداً أقصى للطوابير. بعد استنفاد المحاولات أعد خطأ مؤقتاً مثل `503` أو `409` بحسب العقد، وسجّل `request_id` و`idempotency_key` المنقح دون بيانات الدفع.

## منع الأثر المالي المكرر

ضع قيداً فريداً على `(merchant_id, idempotency_key)`، وخزّن hash للطلب المنطقي. إذا وصل نفس المفتاح مع body مختلف، أعد `409 Idempotency-Key-Reuse` ولا تنفذ المعاملة. إذا كان المفتاح نفسه والـhash نفسه، أعد النتيجة المخزنة أو حالة معالجة واضحة، ولا تنشئ ledger entry ثانية.

## المراقبة

راقب معدل deadlocks، lock wait time، transaction retries، retry exhaustion، rollback rate، duplicate/idempotency conflicts، commit latency، pool saturation، ونتيجة ledger reconciliation. اربطها بـp95/p99 و5xx/429. ارتفاع retries مع ثبات latency قد يسبق الانهيار، وارتفاع deadlocks مع lock wait يدل غالباً على ترتيب أقفال غير ثابت أو معاملات طويلة.

## ما يجب عدم فعله

لا تعالج deadlock بإعادة المحاولة اللانهائية، ولا تعيد POST من العميل بمفتاح جديد، ولا ترسل webhook قبل commit، ولا تسجل SQL parameters أو tokens أو بيانات البطاقة، ولا ترفع حجم pool عشوائياً؛ قد يزيد ذلك التنافس على الأقفال.

## اختبار CI/staging

استخدم payment sandbox وبيانات اصطناعية. اجعل الاختبار يتحقق من أن عدة طلبات بنفس المفتاح تنتج أثراً واحداً، وأن حقن deadlock محدود يؤدي إلى rollback ثم retry ناجح، وأن body مختلف مع المفتاح نفسه يرفض بـ`409`. افصل اختبار deadlock المحقون عن اختبار السعة، واحتفظ بتقارير منقحة قصيرة الاحتفاظ.
